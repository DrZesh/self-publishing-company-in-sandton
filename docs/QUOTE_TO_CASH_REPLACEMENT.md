# Quote-to-cash replacement

The uploaded Quote to Cash module is connected to the production Supabase project and mounted at `/admin/billing`. The Finance menu opens its deals, quotes, invoices and payment screens. Public quote-review links use `/portal/q/:token` on creativebooks.co.za. The staff route uses the existing CRM login and layout.

The original `quote`, `invoice`, `payment`, project and contact tables are retained. Previous financial records are accessible via links at the top of the billing module and `/admin/previous-quotes`, `/admin/previous-invoices` and `/admin/previous-payments`. Existing document-detail routes and public client links remain intact. Historical invoices have not been converted into deposit/balance invoices or repriced.

The migration copies the existing CRM contacts into billing clients with a unique textual `crm_client_id` link, retaining legacy IDs that are not UUIDs. It imports the six catalogue items and company/bank settings supplied in the upload. It does not insert sample quotes, payments or projects. Production never falls back to localStorage demo data. Invoice/payment counters advance beyond existing numeric suffixes; quotes use at least the uploaded starting number 1062.

All ten new billing tables have staff RLS. Except for client maintenance, staff writes run through narrowly scoped RPCs whose private implementations explicitly check `cb_private.is_staff()`. Portal capabilities validate secret UUID tokens and cannot expose drafts. No existing `cb_*` RPC grants are rewritten. Proofs and signed copies use a private, staff-only 10 MB PDF/PNG/JPEG bucket. Payment records require an uploaded proof reference. Client signatures are size-limited PNG data. Quotes calculate totals server-side and reject invalid quantities/discounts. Deposit and balance invoices are transactional; production and final-file status gates require cleared funds.

Opening an email composer does not itself mark a quote sent. The user must return and confirm that the email was sent. Automatic email/WhatsApp delivery and the previous blocked integrations remain disabled. The final-files action updates the workflow status; actual file delivery is still performed by staff. PDF output uses the uploaded browser Print/Save as PDF design. With the supplied blank VAT number, documents are titled INVOICE, without added VAT.

Validation: 48 automated tests passed, including a 26-assertion database workflow/security regression; the production build and billing lint pass. The same 75%/25% workflow was exercised in a live database transaction and rolled back, including invoice generation, payment clearance, project completion and release status. The existing security advisor findings remain unchanged; no new billing findings were introduced. Browser acceptance results are reported with the release.
